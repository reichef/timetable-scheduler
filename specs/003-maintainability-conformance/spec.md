# Feature Specification: Maintainability Conformance of the Existing Code

**Feature Branch**: `003-maintainability-conformance`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "in the last feature I changed the consistution regarding Core Principle I. In this feature i want to adabt the current code to conform to the current version of the constitution"

## Context

Constitution v2.0.0 replaced the former principles "Kotlin Clean Code Standards" and "Test-Driven Development" with
Principle I "Maintainability" (non-negotiable), with three binding parts: clean code (speaking names, small
single-purpose functions, comments on complex-but-compact functions), a readable code layout and test-driven
development. Constitution v2.1.0 made the formatting standard concrete: all Kotlin code must pass ktlint with every
non-experimental standard rule in its default code style (including maximum line length and trailing commas); the
layout rules of v2.0.0 (blank lines between logically connected blocks, bodies of conditionals and loops on their own
indented line) became examples. For this project they are nevertheless enforced automatically as well (clarification
below). The code of features 001 and 002 was written before this
amendment. A survey of the current code base (265 code files, about 26,000 lines, 107 of them test code) found about
190 conditionals and loops with their body on the same line as the condition, about 78 `else` branches written the
same way, and many functions written as one continuous block. This feature brings the existing code into line with
the constitution without changing what the application does.

## Clarifications

### Session 2026-10-22

- Q: Should a violation of the layout rules fail the build or only be reported? → A: It fails the build, locally and in the CI pipeline.
- Q: Should tests for existing functions without a meaningful test be added in this feature? → A: Yes, every non-trivial function found without one gets a meaningful test in this feature.
- Q: How should ktlint's `function-naming` findings for test functions (names written as sentences in backticks) be handled? → A: Ignore them: the rule is disabled for all test sources in one place with the reason (constitution amended to allow disabling for a defined group of files).
- Q: How should this feature treat the layout examples of the constitution (blank lines between steps, conditional and loop bodies on their own line in braces), now that only the ktlint rules are binding? → A: Enforce them automatically as well: project rules for the examples fail the build in addition to ktlint (deliberately stricter than the constitution).

## User Scenarios & Testing *(mandatory)*

The users of this feature are the people who read, review and change the code: the product owner reviewing
AI-generated changes and future developers.

### User Story 1 - Read and review code laid out for humans (Priority: P1)

A reviewer opens any code file of the application and can see the structure of each function at a glance: the steps
of a function are separated by blank lines, every conditional or loop shows its action on its own indented line, and
indentation is consistent. Reviewing a change no longer requires mentally re-formatting dense code.

**Why this priority**: The readable layout is the part of Principle I the existing code violates most often and the
one the product owner explicitly asked for; it affects every file a reviewer opens.

**Independent Test**: Open any code file (production or test) and check it against the layout rules of Principle I;
an automated check over the whole code base reports no layout violation.

**Acceptance Scenarios**:

1. **Given** a conditional whose action was written on the same line (e.g. "if the update changed no row, return
   false"), **When** the reviewer opens the file after this feature, **Then** the action stands on its own line,
   indented one level deeper than the condition and enclosed in braces.
2. **Given** a function that loads data, checks it and stores a result, **When** the reviewer reads it, **Then** the
   three steps are separated by blank lines.
3. **Given** the allowed exceptions of the constitution (a short `if`/`else` used as a value, single-expression
   `when` branches, early exits with the Elvis operator), **When** they occur, **Then** they may stay on one line and
   are not reported as violations.

---

### User Story 2 - Rules stay enforced for future changes (Priority: P2)

When a developer or an AI assistant adds code that breaks the layout rules, this is noticed before the change is
merged, so the code base does not drift away from the constitution again.

**Why this priority**: Without a guard, every later feature (most of them generated by AI) would reintroduce the
same violations; fixing them once is only lasting if they are detected.

**Independent Test**: Introduce a conditional with its action on the same line in a test change; the check reports
it with file and line.

**Acceptance Scenarios**:

1. **Given** a change that violates a layout rule, **When** the checks of the project run, **Then** the violation
   is reported with file and line and the build fails, both locally and in the CI pipeline, so the change cannot be
   merged until it is fixed.
2. **Given** a change that conforms to the rules, **When** the checks run, **Then** no layout violation is reported.

---

### User Story 3 - Clean-code and test findings are resolved (Priority: P3)

A reviewer checks the existing code against the clean-code and test-driven-development parts of Principle I:
general-purpose names (e.g. `data`, `value`, `result` where a domain name fits), functions doing several things,
complex-but-compact functions without an explanatory comment, and functions without meaningful tests. The findings
are recorded and resolved.

**Why this priority**: Features 001 and 002 were already reviewed against the earlier clean-code and TDD principles,
so fewer findings are expected here than for the layout; the remaining ones still have to be closed for full
conformance.

**Independent Test**: The review findings are listed with file and rule; each one is either fixed or explicitly
justified, and the list is empty of open items at the end.

**Acceptance Scenarios**:

1. **Given** a function with a general-purpose parameter name, **When** it is reworked, **Then** the name describes
   the domain meaning.
2. **Given** a long function doing several things, **When** it is reworked, **Then** it is composed of small
   single-purpose functions.
3. **Given** a non-trivial function without a meaningful test, **When** it is found, **Then** a meaningful test is
   added in this feature that pins down its current behaviour.

---

### Edge Cases

- A conditional body consists of an early `return`, `continue`, `break` or `throw` (e.g. "if nothing changed, return
  false"): it is an action, so it moves to its own indented line like any other body; only Elvis-operator exits
  (`?: return`) may stay on one line.
- A conditional is used as a value (e.g. a label chosen by a condition): it may stay on one line if it is short; if
  it spans several lines, each branch follows the layout rules.
- Generated or third-party files (e.g. the build tool's wrapper scripts) are not written by the project and are not
  reformatted.
- The specification documents of earlier features cite the old principle numbers ("Principle V"); they remain as
  historical references and are not rewritten.
- The single small browser script of the application is code of the project and follows the project rules FR-001
  and FR-002; ktlint does not apply to it.
- A ktlint rule cannot be satisfied in a particular place (e.g. a long literal that must not be split): the rule is
  disabled for that file or statement only, with a comment giving the reason (FR-004); each such suppression is
  listed in the review findings.
- A refactoring changes behaviour by mistake: the existing tests and the quickstart scenarios of features 001 and
  002 must reveal it; behaviour changes are not allowed in this feature.
- Log output and error messages must stay free of confidential data (Principle III) after renaming and splitting.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every conditional and loop body in the project's code (production and test code, build scripts and
  the browser script) MUST start on its own line, indented one level deeper than its condition, and MUST be enclosed
  in braces when it spans more than one line; single-line bodies MUST also be enclosed in braces.
- **FR-002**: Within every function, logically connected statements MUST form blocks separated by a single blank
  line; no function body may consist of one continuous block of unrelated steps.
- **FR-003**: The exceptions of the constitution (short `if`/`else` used as a value, single-expression `when`
  branches, Elvis-operator early exits) MAY remain on one line and MUST NOT be reported as violations.
- **FR-004**: All Kotlin code of the project (production, test and build scripts) MUST pass ktlint with every
  non-experimental rule of its standard rule set enabled, in ktlint's default code style (Constitution v2.1.0); this
  covers among others indentation, wrapping, maximum line length and trailing commas. A rule MAY only be disabled with
  a comment giving the reason, for a single statement, a single file or a defined group of files (Constitution
  v2.1.0). ktlint's `function-naming` rule is disabled for all test sources, because test functions are named as
  sentences in backticks that describe the tested behaviour.
- **FR-005**: The project MUST contain an automated check that detects violations of FR-001 – FR-004 and reports
  them with file, line and rule. FR-001 – FR-003 are project rules in addition to ktlint (they turn the
  constitution's layout examples into checked rules); for the browser script, which ktlint does not cover, FR-001 and
  FR-002 are checked as well. The check MUST run as part of the regular build, both locally and in the CI pipeline,
  and any violation MUST fail the build.
- **FR-006**: Names, function size and explanatory comments MUST be reviewed against the clean-code part of
  Principle I; every finding MUST be fixed or explicitly justified, and the findings with their resolution MUST be
  recorded.
- **FR-007**: Every non-trivial function without a meaningful test MUST be identified and get a meaningful test in
  this feature that pins down its current behaviour (test-driven-development part of Principle I); the list of
  functions found and their new tests MUST be recorded.
- **FR-008**: The behaviour of the application MUST NOT change: all existing automated tests MUST pass without
  changing what they assert, and the quickstart scenarios of features 001 and 002 MUST still pass.
- **FR-009**: Confidentiality rules (Principle III) MUST continue to hold: no renaming or restructuring may add
  confidential data to logs or technical error output.
- **FR-010**: The project documentation MUST describe how to run the layout check and how to fix reported
  violations.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: The automated layout check reports 0 violations over the whole code base at the end of the feature
  (starting point: about 190 conditionals and loops and about 78 `else` branches with same-line bodies, plus several
  hundred ktlint findings, mainly line length and trailing commas; the exact count is recorded when the check is
  first run).
- **SC-002**: 100 % of the existing automated tests pass after the change, with no test assertion weakened or
  removed.
- **SC-003**: All quickstart scenarios of features 001 and 002 pass after the change, with the same results as
  before.
- **SC-004**: A deliberately introduced layout violation is detected by the check and fails the build in 100 % of
  trial cases (one case per project rule of FR-001 – FR-003 and one each for ktlint's indentation, line-length and
  trailing-comma rules), locally and in the CI pipeline.
- **SC-005**: Every clean-code finding of the review (FR-006) is either fixed or carries a written justification;
  0 findings remain open.
- **SC-006**: A reviewer can locate the steps of any function of at least 10 lines by its blank-line separated
  blocks; in a sample of 20 randomly chosen functions, every one meets FR-002.
- **SC-007**: 0 non-trivial functions without a meaningful test remain; every function found without one has a new
  test that passes.

## Assumptions

- "The project's code" means all code written for the project: production and test code of all modules, the build
  scripts and the browser script. Generated files and files of third parties are excluded.
- Existing tests are the safety net for the refactoring; their assertions are not changed, only their layout and
  names. New tests pin down the current behaviour of previously untested functions; if one reveals a defect, the
  defect is recorded and fixed in a separate change, not silently in this refactoring.
- The work is done on a separate branch and delivered as one pull request; it may be split into several commits
  (e.g. per module) to keep review manageable.
- The maximum line length and all other formatting details follow ktlint's default code style (FR-004); the product
  owner accepts that this changes several hundred lines.
- Making the constitution's layout examples a checked rule is a project decision stricter than the constitution;
  it does not change the constitution.
- No new functionality and no new user-visible text are introduced.
