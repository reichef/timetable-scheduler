# Timetable Scheduler Constitution

## Core Principles

### I. Maintainability (NON-NEGOTIABLE)

Most of the code is generated by AI, but humans have to read, review, understand and change it. Every piece of
production and test code MUST therefore be written so that a human can maintain it without the help of the tool that
generated it. Maintainability has three parts, all of them binding.

**Clean code (Kotlin).** We follow clean code standards for Kotlin.

- Functions, parameters and variables MUST use speaking, domain-specific names (e.g. `teacherAvailability`,
  `classWeighting`) instead of general-purpose names (e.g. `data`, `payload`, `value`).
- Functionality MUST be composed of small, single-purpose functions rather than large multi-purpose functions.
- Every function whose logic is complex but compact (e.g. constraint checks, scheduling/optimization routines, usage
  of flow operators) MUST carry a comment explaining what it does and why.

**Readable code layout.** Code MUST be laid out for human reading, not for density.

- **Formatting standard**: all Kotlin code (production, test and build scripts) MUST pass **ktlint** with every
  non-experimental rule of its standard rule set enabled, in ktlint's default code style. This includes, among
  others, indentation, wrapping, maximum line length and trailing commas. Experimental rules are not used. A rule
  MAY only be disabled with a comment giving the reason, and only for a single statement, a single file or a defined
  group of files (e.g. all test sources in the formatter configuration) for which the same reason holds.
- **Examples** of the layout this aims for — they illustrate the intent and guide reviews and new code; the binding
  formatting rules are those of the formatting standard above:
  - Logically connected statements form a block, and blocks inside a function are separated by a single blank line
    (e.g. loading the input, checking it, computing the result, storing or answering) instead of writing a function
    as one continuous block of unrelated steps.
  - The body of a conditional or loop starts on its own line, indented one level deeper than the condition and
    enclosed in braces:

    ```kotlin
    if (generation.isRunning) {
        control.requestStop(generationId)
    }
    ```

    instead of `if (generation.isRunning) control.requestStop(generationId)`. Expressions rather than actions —
    a short `if`/`else` used as a value (`val label = if (dropped) droppedText else lessonText`), single-expression
    `when` branches (`Role.PLANNER -> plannerHome`) and early exits with the Elvis operator (`?: return`) — may stay
    on one line.

**Test-driven development.** For every function, meaningful, non-trivial tests MUST be written before the
implementation and MUST pass after it. We do not aim for a code-coverage figure but for tests that pin down the
behaviour, especially of complex functionality.

Rationale: generated code is cheap to produce but expensive to maintain; clear names, small functions, a layout that
shows the structure of a function at a glance, and tests that document the expected behaviour keep the code
changeable by humans.

### II. Tool and Library Use Where Appropriate

Use existing open-source tools and libraries when creating functionality. However, introduce as few dependencies as
possible (i.e. do not use libraries for trivial functionality).

### III. Confidentiality & Data Protection (NON-NEGOTIABLE)

The application stores and processes confidential information, e.g., about teachers and school classes. Access to
this data MUST be protected by authentication, and operations on it MUST be authorized against the requesting user's
role. Confidential data MUST NOT appear in logs, stack traces, or diagnostic output. Persisted data MUST be protected
by access control or by encryption.

Error messages are treated by kind:

- Business (domain) error messages that explain why a user action was rejected (e.g., "Subject cannot be deleted:
  still taught by teacher Anna Schmidt") MAY contain confidential data, but only data the requesting user is
  authorized to see (e.g., the planner of that school) and only as much as needed to resolve the problem. Such
  messages MUST NOT be written to logs with their confidential content.
- Technical and unexpected error messages (e.g., exceptions, database or infrastructure failures) MUST NOT contain
  confidential data, neither when surfaced to users nor in logs; they show a generic message and a correlation id
  only.

Any export, report, or API response MUST include only the minimum data necessary for its purpose.

### IV. Pareto-Optimal Scheduling Integrity

The purpose of the application is to create Pareto-optimal solutions across the competing objectives of filling every
class's timetable as well as possible, without ever violating a defined hard constraint (e.g. a teacher
double-booked, a class scheduled outside available slots). A produced solution set MUST allow the user to compare
trade-offs between Pareto-optimal alternatives rather than silently collapsing them into a single "best" answer
(Pareto curve).

## Technology & Architecture Constraints

- Language & build: Kotlin on Gradle is the only supported language/build toolchain for production code. We use a
  CI/CD pipeline on GitHub for this purpose.
  Exception: small static browser scripts (plain JavaScript served as a static resource of the application) are
  allowed when an interaction cannot be realized with server-rendered HTML alone. Such scripts MUST NOT require a
  build tool, package manager, transpiler or third-party library, MUST NOT contain business, validation, scheduling
  or access logic (these stay in Kotlin), MUST NOT process or store confidential data, and the application MUST
  remain usable when they are disabled (progressive enhancement). Each script stays small and single-purpose and is
  checked in review like any other code, including the layout examples of principle I (ktlint applies to Kotlin
  only).
- Clean architecture: We use the clean architecture for structuring the application. Thus, we have circles like
  entities (most inner circle), the application specific business rules, interface adapters and the frameworks &
  drivers (most outer circle). Dependencies point only from outer circles to inner ones.
- Database: any relational or embedded database is acceptable provided it supports transactional writes and access
  control sufficient to satisfy Principle III. The specific engine is an implementation detail.
- Secrets and credentials (database connection strings, auth tokens) MUST NOT be committed to the repository and
  MUST be supplied via configuration external to source control.
- Security testing: We use static application security testing tools to detect security issues. First, we use
  CodeQL with its basic security suite for basic security testing in the CI/CD pipeline. Second, we use GitHub
  Advanced Security as software composition analysis. Still, the CI/CD pipeline and the project structure have to
  be designed in a way that also other tools can be used.

## Development Workflow & Quality Gates

- The formatting standard of principle I (ktlint, all non-experimental standard rules) MUST be checked
  automatically by the build; a violation MUST fail the build locally and in the CI pipeline.
- Code review MUST verify principle I: descriptive naming, function size/single-purpose decomposition, explanatory
  comments on complex-but-compact functions, a layout that reads like the examples of principle I (blank lines
  between logical blocks, conditional and loop bodies on their own line) and tests written for every new or changed
  behaviour.
- Code review MUST verify the absence of confidential data in logs and in technical/unexpected error output
  (business error messages only with data the user is authorized to see, per Principle III).
- Changes to scheduling constraints or weighting logic MUST include tests demonstrating hard constraints are never
  violated and that Pareto comparisons behave as intended.
- Changes to persisted entities MUST include the corresponding database migration in the same change set.
- UI changes MUST be verified against a running instance of the application before being reported as complete.
- New features, fixes, and improvements will be developed in a separate branch. NO work will be directly performed
  on the main branch.

## Governance

This constitution supersedes all other project practices and guidelines, including AGENTS.md, where a conflict
exists; AGENTS.md continues to govern day-to-day style details not covered here. Amendments require: (1) a
documented rationale for the change, (2) an update to this file including the Sync Impact Report, and (3) a version
bump per the policy below. Versioning follows semantic versioning: MAJOR for backward-incompatible principle removals
or redefinitions, MINOR for new principles or materially expanded guidance, PATCH for clarifications and wording
fixes. All pull requests and reviews MUST verify compliance with this constitution; unjustified complexity or
deviation from a principle MUST be called out and either resolved or explicitly justified in the review.
